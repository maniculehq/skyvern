When you self-host Skyvern, the secrets behind every Skyvern credential record (passwords, TOTP keys, card numbers) live in *your* vault, not in Skyvern's database. Skyvern only stores friendly metadata and fetches the real value at runtime. This page is for self-hosted operators picking the storage backend used by `create_credential` and wiring up its env vars. By the end, you should know which vault to choose and exactly which variables to set on the Skyvern container.

If you're on Skyvern Cloud, this is handled for you and you can ignore this page; see [Store Credentials](/developers/credentials/store-credentials) instead.

## What "vault" means here

`CREDENTIAL_VAULT_TYPE` (`skyvern/config.py:434`) selects which backend Skyvern calls when it needs to read a secret. Three values are accepted today:

| Value | Backend |
|---|---|
| `bitwarden` (default) | Bitwarden, Vaultwarden, or Skyvern's vendored Bitwarden CLI server. |
| `azure_vault` | Azure Key Vault. |
| `custom` | Your own HTTP service, called via `skyvern/forge/sdk/api/custom_credential_client.py`. |

1Password is a separate code path, not a `CREDENTIAL_VAULT_TYPE`. Skyvern can resolve 1Password items for login helpers and workflow credential parameters when `OP_SERVICE_ACCOUNT_TOKEN` is set (`config.py:431`), but `create_credential` stores only in `bitwarden`, `azure_vault`, or `custom`.

The credential record itself (`CredentialModel`, `forge/sdk/db/models.py:1081-1105`) keeps a `vault_type` and an `item_id` so different rows can route to different providers.

## Picking a backend

| You want | Pick |
|---|---|
| Default storage path with the vendored CLI bridge. | `bitwarden` with the bundled Bitwarden CLI server pointed at Bitwarden or Vaultwarden. |
| Existing Bitwarden Enterprise / self-hosted Vaultwarden. | `bitwarden` pointed at it. |
| Azure-native deployment with Key Vault as the secrets store. | `azure_vault`. |
| Use 1Password item references in login blocks or workflow parameters. | Keep your default backend, set `OP_SERVICE_ACCOUNT_TOKEN`, and pass 1Password item IDs where those APIs accept them. |
| HSM, on-prem, or non-standard secret manager. | `custom` and implement the HTTP contract. |

## Bitwarden / Vaultwarden

Bitwarden (or its open-source companion Vaultwarden) is the default. Skyvern reaches it through the Bitwarden CLI; the repo ships a containerized CLI under `bitwarden-cli-server/` so you don't have to install one on your host.

Set the connection coordinates and the service-account credentials Skyvern uses when storing API-created credentials:

```bash .env
CREDENTIAL_VAULT_TYPE=bitwarden

# Where the Bitwarden CLI server is reachable.
BITWARDEN_SERVER=http://bitwarden-cli-server
BITWARDEN_SERVER_PORT=8002

# Credentials Skyvern uses for API-created credential records.
SKYVERN_AUTH_BITWARDEN_ORGANIZATION_ID=<organization-id>
SKYVERN_AUTH_BITWARDEN_CLIENT_ID=user.<id>
SKYVERN_AUTH_BITWARDEN_CLIENT_SECRET=<secret>
SKYVERN_AUTH_BITWARDEN_MASTER_PASSWORD=<password>

# On the bitwarden-cli-server container, point the CLI at your vault.
BW_HOST=https://your-vaultwarden-or-bitwarden-host
BW_CLIENTID=user.<id>
BW_CLIENTSECRET=<secret>
BW_PASSWORD=<password>
```

`BITWARDEN_SERVER` and `BITWARDEN_SERVER_PORT` come from `config.py:453-454`; the `SKYVERN_AUTH_BITWARDEN_*` variables are at `config.py:448-451`. If you're using the bundled CLI server, point Skyvern at its container hostname and leave the port at `8002`. The CLI server then uses `BW_HOST` to decide whether it talks to Vaultwarden, self-hosted Bitwarden, or hosted Bitwarden.

When a Skyvern run needs a Bitwarden-backed credential, the worker logs into the CLI with these creds, fetches the secret, fills the form, and forgets it. Tune retries with `BITWARDEN_MAX_RETRIES`, `BITWARDEN_RETRY_*` if your CLI is on a flaky network.

<Note>
The `BITWARDEN_CLIENT_ID`, `BITWARDEN_CLIENT_SECRET`, `BITWARDEN_MASTER_PASSWORD`, and `BITWARDEN_EMAIL` variables (`config.py:427-431`) are for direct Bitwarden login references in workflow parameters and helper APIs. They are not the storage credentials used by `create_credential`.
</Note>

## Azure Key Vault

Use this when your secrets already live in Azure Key Vault and you want a single source of truth.

```bash .env
CREDENTIAL_VAULT_TYPE=azure_vault

# Service principal Skyvern uses to authenticate.
AZURE_TENANT_ID=<tenant-uuid>
AZURE_CLIENT_ID=<app-uuid>
AZURE_CLIENT_SECRET=<client-secret>

# Key Vault name (not the full URL).
AZURE_CREDENTIAL_VAULT=skyvern-prod
```

These variables are at `config.py:437-441`. The service principal needs `get` and `list` permissions on the vault's secrets. Each Skyvern credential row stores the *secret name* it should read; the service principal supplies the rest.

If you're already running Skyvern with Azure OpenAI, you can reuse the same service principal as long as it has the right Key Vault permissions; the `AZURE_*` env vars are read once per process.

## 1Password

1Password works alongside any default backend for direct external references. Set the token:

```bash .env
OP_SERVICE_ACCOUNT_TOKEN=ops_eyJ...
```

Then pass `credential_type="1password"` with `onepassword_vault_id` and `onepassword_item_id` to login helpers or workflow credential parameters that support direct external references. At runtime Skyvern resolves the item with the service account token and never persists the secret. Do not pass `vault_type="1password"` to `create_credential`; the accepted create-time storage backends are `bitwarden`, `azure_vault`, and `custom`.

## Custom credential service

When neither built-in backend is acceptable (HSM-backed secrets, on-prem secret manager, internal API), point Skyvern at a custom HTTP endpoint instead.

```bash .env
CREDENTIAL_VAULT_TYPE=custom

CUSTOM_CREDENTIAL_API_BASE_URL=https://secrets.internal/skyvern
CUSTOM_CREDENTIAL_API_TOKEN=<bearer-token>
```

The two variables are at `config.py:444-445`. Skyvern's client at `skyvern/forge/sdk/api/custom_credential_client.py` calls your service with the bearer token and a credential ID; your service returns the secret payload (password, TOTP, card data) Skyvern then injects into the browser. Implementing the contract is out of scope for this page; read the client module before building yours.

## When the vault is unreachable

Vault failures are *not* retried. If the vault returns an error or the connection times out, the in-flight run fails with the vault's own error message bubbled up; subsequent runs attempting the same credential will keep failing until the vault recovers.

For the custom backend, `skyvern/forge/sdk/api/custom_credential_client.py:73-82, 336-345` is explicit about this: the client extracts whichever of `message`, `error`, `detail`, or `error_message` is present in the response body and raises an `HttpException` with that string; if none are present it falls back to the HTTP status code. Whatever message you ship from your custom service is what the user sees in the Skyvern UI. Make those messages diagnostic; a bare `500` from your secret manager will produce a bare Skyvern run failure.

The Bitwarden CLI server *does* retry within `BITWARDEN_MAX_RETRIES` for transient CLI errors, but that's the only retry layer; once the CLI surfaces a final failure, Skyvern fails the run immediately. Plan vault reliability accordingly: a 30-second secret-manager outage during a run *will* fail that run.

## Verifying the wiring

Once your env vars are in place, restart the Skyvern container and create a test credential through the API:

```python
import os
from skyvern import Skyvern

client = Skyvern(api_key=os.getenv("SKYVERN_API_KEY"), base_url="http://localhost:8000")

credential = await client.create_credential(
    name="Vault Smoke Test",
    credential_type="password",
    credential={"username": "test@example.com", "password": "hunter2"},
)
print(credential.credential_id)
```

If `CREDENTIAL_VAULT_TYPE=bitwarden`, the secret should appear in your Bitwarden vault as a new login item. If `azure_vault`, it should appear as a Key Vault secret. If neither shows up, the Skyvern logs will report the auth failure with the exact env var that's missing or wrong; structlog tags every line with the vault type so the message is easy to grep.
