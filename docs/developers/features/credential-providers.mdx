Skyvern can pull authentication material from one of five backends. Which one a workflow uses is determined by the `CredentialType` value attached to the credential, and Skyvern routes the request to the matching client at fire time. This page is the map: which type means what, what config it needs, and which features only work on certain backends.

`CredentialType` is defined in `skyvern/schemas/run_blocks.py:8-12`:

```python
class CredentialType(StrEnum):
    skyvern = "skyvern"           # Skyvern's own encrypted vault
    bitwarden = "bitwarden"       # Bitwarden organization vault
    onepassword = "1password"     # 1Password service-account
    azure_vault = "azure_vault"   # Azure Key Vault
```

Plus one more that does not appear in the enum: a **custom HTTP credential service** that you run yourself. Skyvern reaches it through `skyvern/forge/sdk/api/custom_credential_client.py`. You opt in by setting `CUSTOM_CREDENTIAL_API_BASE_URL`; there is no public `CredentialType` value for it because it intentionally looks like a generic HTTP fetch to the rest of the system.

## Decision tree

- **You want Skyvern to manage everything end-to-end.** Use `CredentialType.skyvern`. Lowest setup cost; credentials are stored encrypted in the Skyvern database.
- **You already use Bitwarden for secrets.** Use `CredentialType.bitwarden`. You keep one source of truth and Skyvern reads through the Bitwarden CLI proxy.
- **You already use 1Password.** Use `CredentialType.onepassword` with a service-account token. Same story as Bitwarden.
- **You are an Azure shop and want secrets in Key Vault.** Use `CredentialType.azure_vault`. Required if your security review needs HSM-backed storage.
- **You have a homegrown secrets service** (Vault, AWS Secrets Manager behind a translator, etc.). Stand up an HTTP wrapper and point Skyvern at it via `CUSTOM_CREDENTIAL_API_BASE_URL`.

If none of those fit, default to `CredentialType.skyvern`.

## Skyvern vault

The default. Credentials live in the `CredentialModel` table (`skyvern/forge/sdk/db/models.py:1081`), encrypted at rest with AES using the `ENCRYPTOR_AES_*` settings.

| Setting | Purpose |
|---|---|
| `ENCRYPTOR_AES_SECRET_KEY` | AES key. Default `"fillmein"` — replace before production. |
| `ENCRYPTOR_AES_SALT` | AES salt. |
| `ENCRYPTOR_AES_IV` | AES IV. |

Skyvern-vault credentials support every credential shape: passwords, credit cards, TOTP, and free-form sensitive payloads. CRUD goes through `/v1/credentials/...`. The vault is automatically used when no other provider is configured for the credential.

## Bitwarden

Bitwarden is the default `CREDENTIAL_VAULT_TYPE`. Skyvern reads through the Bitwarden CLI, fronted by a small HTTP proxy (`bitwarden-cli-server/`), so it does not need to ship the Bitwarden CLI inside the FastAPI process.

| Setting | Purpose |
|---|---|
| `CREDENTIAL_VAULT_TYPE` | Defaults to `bitwarden`. Set to `azure_vault` to flip the default. |
| `BITWARDEN_CLIENT_ID` / `BITWARDEN_CLIENT_SECRET` | Bitwarden API auth. |
| `BITWARDEN_MASTER_PASSWORD` / `BITWARDEN_EMAIL` | Bitwarden vault unlock. |
| `BITWARDEN_SERVER` / `BITWARDEN_SERVER_PORT` | Address of the Bitwarden CLI proxy. Defaults to `http://localhost:8002`. |
| `BITWARDEN_TIMEOUT_SECONDS` / `BITWARDEN_MAX_RETRIES` / `BITWARDEN_MAX_JITTER_SECONDS` | Retry knobs. |

Bitwarden credentials are also exposed through dedicated routes for the dashboard's collection picker (`/v1/credentials/bitwarden/...`, around `credentials.py:1632-1900`).

## 1Password

Set up a 1Password service account with read-only access to the vaults Skyvern needs:

| Setting | Purpose |
|---|---|
| `OP_SERVICE_ACCOUNT_TOKEN` | Service-account token from 1Password. |

The `onepassword-sdk` Python package handles the protocol. Credentials are referenced by their 1Password item id when assigned to a workflow.

## Azure Key Vault

Use Azure Key Vault when the rest of your stack already runs in Azure or your security policy requires HSM-backed storage.

| Setting | Purpose |
|---|---|
| `CREDENTIAL_VAULT_TYPE` | Set to `azure_vault`. |
| `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET` | Azure AD app auth. |
| `AZURE_CREDENTIAL_VAULT` | The Key Vault name. |

Skyvern caches secret material per-process for the duration of a run, so a Key Vault-backed credential does not result in a Key Vault read on every step.

## Custom HTTP credential service

If your secrets live somewhere Skyvern does not natively support (HashiCorp Vault, AWS Secrets Manager, an internal microservice), point Skyvern at an HTTP shim:

| Setting | Purpose |
|---|---|
| `CUSTOM_CREDENTIAL_API_BASE_URL` | Base URL of your shim (e.g. `https://secrets.internal/`). |
| `CUSTOM_CREDENTIAL_API_TOKEN` | Bearer token Skyvern sends in `Authorization`. |

The shim must speak the contract documented in `custom_credential_client.py`: respond to `GET /credentials/{id}` with the credential payload and `200`, return `404` when the id is unknown, and never block longer than the request timeout. The custom client is the "trapdoor" provider; Skyvern does not write to it, only reads.

## Provider-by-feature matrix

| Feature | Skyvern | Bitwarden | 1Password | Azure Vault | Custom HTTP |
|---|---|---|---|---|---|
| Password (username + password) | yes | yes | yes | yes | yes |
| Credit card | yes | yes | yes | yes | yes |
| TOTP code | yes | yes | yes | partial[^1] | yes |
| Cloud-only sharing | yes | yes | yes | yes | depends on your shim |
| Self-hosted support | yes | yes | yes | yes | yes |
| Skyvern-side rotation | yes | no | no | no | no |
| Per-workflow scoping | yes | yes (via collection) | yes | yes | yes |

[^1]: Azure Key Vault stores the TOTP secret as a generic string; Skyvern computes the code at fire time. There is no built-in TOTP rotation.

## How `page.agent.login` picks a provider

The login helper has overloads for each provider (`skyvern/library/skyvern_browser_page_agent.py:102-180`):

```python
# Skyvern vault
await page.agent.login(credential_id="cred_abc")

# Bitwarden by item id
await page.agent.login(bitwarden_credential_id="bw_item_xyz")

# 1Password by item id
await page.agent.login(onepassword_vault_id="...", onepassword_item_id="...")

# Azure Key Vault by secret name
await page.agent.login(azure_vault_secret_name="prod-billing-login")
```

Pick the overload that matches your provider. The helper wires the credential through to the agent's prompt, so the LLM never sees the secret directly; Skyvern injects it at the action layer.
