When Skyvern's agent completes an eligible task or workflow, it records the actions it took and generates reusable code from them. Later code-mode runs can execute that cached code directly, skipping LLM inference and screenshot analysis. This lowers repeated-run inference cost and makes behavior more deterministic. If the cached code fails because a page changed, Skyvern can fall back to the agent and regenerate the cache when `ai_fallback` is enabled.

## How it works

For a task-first flow, set `engine="skyvern-2.0"`, `publish_workflow=True`, and `run_with="code"` so Skyvern can publish the successful run as a workflow-backed script:

```python
result = await client.run_task(
    prompt="Extract the latest invoice total from the portal.",
    url="https://portal.example.com",
    engine="skyvern-2.0",
    publish_workflow=True,
    run_with="code",
    wait_for_completion=True,
)
```

For saved workflows, set the workflow's `run_with` field to `code` or pass `run_with="code"` when starting a run:

```python
run = await client.run_workflow(
    workflow_id="wpid_abc123",
    parameters={"target_url": "https://portal.example.com"},
    run_with="code",
)
```

On subsequent runs, pass `run_with="code"` to execute the cached code directly. On a cache hit, Skyvern replays the recorded action sequence instead of asking the LLM for every step.

If the cached code hits something unexpected (a layout change, a new field, a missing element), Skyvern re-runs with the full agent and can regenerate the cache when `ai_fallback=true`. That is the default for normal code-mode runs and is forced on the adaptive caching path. If you set `ai_fallback=false` on a non-adaptive run, the failure is returned instead.

<Note>
The SDK default engine is `skyvern-1.0`. To start from a task, explicitly set `engine="skyvern-2.0"` and publish the successful run as a workflow. In the Cloud UI, `skyvern-2.0` is the default task engine.
</Note>

## What gets cached

**Tasks** cache the full action sequence the agent took: clicks, form fills, extractions, and navigation.

**Workflows** cache per block. Each block that successfully executes gets its own cached script, so a partially-cached workflow still saves time on the blocks that have been seen before.

**Progressive caching** handles workflows with conditionals. Run 1 covers branch A, run 2 covers branch B, and so on. Previous caches are preserved, so coverage builds up over time.

**Not cached:** wait blocks, code blocks, control scaffolding, and blocks marked `disable_cache` or `requires_agent` run live because their behavior depends on runtime state. Conditional branches can build coverage over time through progressive caching.

<Tip>
Pair cached code with [scheduled workflows](/cloud/building-workflows/scheduling) for cheap, reliable recurring runs. The first scheduled run builds the cache, and every subsequent run executes from it.
</Tip>
