A Script is a snapshot of a workflow run, captured as Playwright code Skyvern generated by watching the agent execute the workflow once. On the next run, Skyvern can re-execute that code instead of asking the LLM what to do, which is faster, cheaper, and deterministic. When the code fails (because the page changed), Skyvern can fall back to the agent for the failing block and re-publish a new revision.

The single-page concept here ([Code caching](./code-caching)) covers the high-level workflow flag. This page goes one level deeper: the public REST surface that exposes Scripts as first-class objects, and how the lifecycle works.

## What "Script" means in the API

Every workflow can have one or more Scripts. A Script has versions (revisions), each with files. The shape lives in `skyvern/schemas/scripts.py`:

- `Script` — the long-lived script identity (`script_id`).
- `ScriptRevision` — one immutable version (`script_revision_id`, `version` integer).
- `ScriptFile` — one file inside a revision: path, mime type, content hash, encoding (`utf8` or `base64`), and a pointer to the artifact storing the bytes.
- `ScriptBlock` — links a workflow block label to the file that implements it.
- `WorkflowScript` — the binding between a workflow and a script, including `cache_key`, `cache_key_value`, `status` (`pending` or `published`), and a pin flag.
- `ScriptFallbackEpisode` — a record of a single block falling back to the agent, plus the agent's actions and an optional reviewer recommendation.

The `cache_key_value` is what Skyvern uses to decide whether two runs should share a Script. By default the key is `default`, meaning every run shares one cached version. Workflows that fork on a parameter (e.g. one Script per region) can override the key to keep the variants separate.

## Two ways code caching turns on

You opt in to cached execution at run time, not on the workflow itself. There are two flags:

- `run_with` — `"code"` to require cached code, `"agent"` to require the LLM, `None` (default) to let Skyvern decide.
- `ai_fallback` — `True` to let cached code fall back to the agent on a per-block basis when something throws.

```python
# Use cached code if it exists, fall back to the agent if it breaks.
result = await client.run_workflow(
    workflow_id="wpid_daily_report",
    run_with="code",
    ai_fallback=True,
    wait_for_completion=True,
)
```

If a fallback fires, Skyvern records a `ScriptFallbackEpisode` and surfaces the original failure plus the recovery actions in the run timeline. The next time you call [`script_reviewer`](#script-reviewer) (or the dashboard's "review" button), Skyvern can roll those fallbacks into a new revision.

## Lifecycle

A workflow's first run with `run_with="code"` and `ai_fallback=True` creates the initial `WorkflowScript`. The lifecycle from there is:

1. **Pending** — Skyvern captures the agent's actions during the first run and writes them as a draft Script revision. `status="pending"`.
2. **Deploy** — calling `POST /v1/scripts/{script_id}/deploy` (`deploy_script`) promotes the latest revision and flips `status` to `published`. Subsequent runs that match the cache key now execute code first.
3. **Fallback** — when a block in published code raises, the agent takes over for that one block. Skyvern writes a `ScriptFallbackEpisode`.
4. **Review** — `script_reviewer.review_script` analyzes the fallback episodes and proposes an updated revision. The reviewer's diff lands as a new `pending` revision; deploy it to promote.
5. **Pin** — calling `POST /v1/scripts/{script_id}/pin` locks a revision in place so the reviewer cannot bump it. Useful when you have a known-good version and want to opt out of automatic updates.

## REST surface

Every endpoint lives under `/v1/scripts` and is tagged `Scripts` in the OpenAPI.

| Method + path | Purpose |
|---|---|
| `POST /v1/scripts` | Create a new Script with an initial set of files. Body: `CreateScriptRequest` (`workflow_id`, `run_id`, `files`). |
| `GET /v1/scripts` | List Scripts visible to the org. |
| `GET /v1/scripts/{script_id}` | Fetch one Script and its current revision. |
| `POST /v1/scripts/{script_id}/deploy` | Promote the latest pending revision to published. Body: `DeployScriptRequest` (`files`). |
| `POST /v1/scripts/{script_id}/run` | Execute a script directly. Mostly useful for ad-hoc replay; production runs use `run_workflow(run_with="code")`. |
| `DELETE /v1/scripts/{workflow_permanent_id}/cache` | Clear cached scripts for a workflow. Returns `ClearCacheResponse` with the deleted count. |

A few endpoints worth calling out:

### Cache clear

When the page you automate changes shape and you do not want the agent to fall back through every block on the next run, clear the cache:

```python
deleted = await client.scripts_clear_workflow_cache("wpid_daily_report")
print(f"Cleared {deleted.deleted_count} cached scripts")
```

The next run with `run_with="code"` finds nothing to replay and is forced to use the agent, regenerating the Script from scratch.

### Pin a revision

When you have a known-good revision and want it to keep running even if the reviewer proposes changes:

```python
await client.scripts_pin(
    script_id="scr_abc123",
    cache_key_value="default",
)
```

Pinning sets `is_pinned=true` and records `pinned_at` / `pinned_by`. Unpinning re-enables the auto-promotion path.

### Script reviewer

After a few fallback episodes accumulate, ask the reviewer for an update:

```python
result = await client.scripts_review(
    script_id="scr_abc123",
    user_instructions="Update the selector for the date picker.",
    workflow_run_id="wr_xyz",
)
print(result.updated_blocks)
```

The reviewer reads the failing block's HTML snapshots and the agent's recovery actions, then proposes a revised file. The result lands as a `pending` revision; deploy it to make it active.

## When code caching is the wrong tool

Code caching shines on flows that look the same every time: scheduled reports, monthly invoice pulls, idempotent "fill this form with these fields" automations. It is the wrong tool when:

- the page layout changes for every run (search results pages, A/B tested checkout flows);
- the prompt itself varies (`run_task` with a different `prompt` each call);
- you only run the workflow a handful of times. The cost of generating and reviewing the Script outweighs the savings.

For those, run the agent directly (`run_with="agent"` or omit `run_with`) and skip the Script lifecycle.
