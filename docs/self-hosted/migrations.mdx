Skyvern uses [Alembic](https://alembic.sqlalchemy.org/) to manage all PostgreSQL schema changes. Every version upgrade that touches the database ships as an Alembic migration; there are **184 migrations** as of v1.0.29.

<Note>
**Run migrations before starting a new server version.** Starting the server on an older schema will cause runtime errors.
</Note>

---

## Prerequisites

- PostgreSQL is running and `DATABASE_STRING` is set in your environment or `.env` file.
- The `skyvern` Python package is installed (`uv sync` or `pip install skyvern`).
- You are in the root of the Skyvern repository (where `alembic.ini` lives).

`DATABASE_STRING` uses the SQLAlchemy / psycopg connection URL format:

```
postgresql+psycopg://USER:PASSWORD@HOST:PORT/DATABASE
```

Example for a local install:

```bash
export DATABASE_STRING="postgresql+psycopg://skyvern:skyvern@localhost:5432/skyvern"
```

## Running migrations

### Apply all pending migrations

```bash
alembic upgrade head
```

This brings your schema to the latest revision. It is idempotent — running it again when you are already at `head` is safe and makes no changes.

**Upgrading across multiple versions** — `alembic upgrade head` applies every pending migration in chain order. You do not need to run migrations one version at a time. Whether you are one release or twenty behind, a single `alembic upgrade head` catches you up safely.

### Check the current revision

```bash
alembic current
```

Output includes the revision hash and whether the database is at `head`.

### Apply a specific revision

```bash
alembic upgrade <revision>
```

Replace `<revision>` with the short hash shown in `alembic current` or the filename prefix in `alembic/versions/`.

### Roll back one revision

```bash
alembic downgrade -1
```

### Roll back to a specific revision

```bash
alembic downgrade <revision>
```

<Warning>
Downgrading may be irreversible if a migration performed a data transformation. Always back up your database before rolling back in production.
</Warning>

## Migration files

Migrations live in `alembic/versions/`. Each file is a Python module with `upgrade()` and `downgrade()` functions:

```
alembic.ini           # Alembic configuration — lives at the repo root
alembic/
  env.py              # Runtime environment — loads settings, imports models
  script.py.mako      # Migration template
  versions/
    0001_initial.py
    0002_add_tasks.py
    ...               # 184 revisions total as of v1.0.29
```

Migration files are named `<hash>_<description>.py`. The chain is linear; each file declares its predecessor via `down_revision`.

## Docker Compose

If you run Skyvern with the provided `docker-compose.yml` (see [Docker Deployment](/self-hosted/docker)), migrations run automatically when the server container starts:

```yaml
# excerpt from docker-compose.yml
command: skyvern quickstart
```

`skyvern quickstart` calls `alembic upgrade head` before starting the server process. You do not need to run migrations manually in Docker Compose deployments.

To verify after a restart:

```bash
docker compose exec skyvern alembic current
```

## Kubernetes

If you deploy Skyvern on [Kubernetes](/self-hosted/kubernetes), run migrations as an init container or a one-off Job before the main Deployment rolls out. Example init container:

```yaml
initContainers:
  - name: run-migrations
    image: skyvern/skyvern:latest
    command: ["alembic", "upgrade", "head"]
    envFrom:
      - secretRef:
          name: skyvern-env
```

This ensures the schema is up to date before any application Pod starts.

## Creating a new migration

<Note>
This section is for contributors modifying Skyvern's source code. If you are operating a self-hosted deployment without making code changes, you do not need to create migrations — only run the existing ones with `alembic upgrade head`.
</Note>

If you are developing Skyvern locally and modify SQLAlchemy models, generate a migration automatically:

```bash
alembic revision --autogenerate -m "add_new_column_to_tasks"
```

Review the generated file in `alembic/versions/` before committing — `--autogenerate` can miss complex changes such as partial indexes or custom types.

## Troubleshooting

The errors below cover the most common issues when running `alembic` commands.

### `Can't locate revision identified by '<hash>'`

Your `alembic_version` table references a revision that no longer exists in `alembic/versions/`. This happens if you switch branches or pull a partial set of migrations. Run `git log --oneline alembic/versions/` to confirm which revisions are present, then check out the missing files.

### `Target database is not up to date`

The server printed this error on startup, or a migration check tool reported it. Run `alembic upgrade head` and restart.

### `psycopg.OperationalError: connection refused`

Alembic cannot reach the database. Confirm `DATABASE_STRING` is set correctly and that PostgreSQL is running:

```bash
echo $DATABASE_STRING
psql "$DATABASE_STRING" -c "SELECT 1"
```

### Permission errors on schema changes

Alembic requires `CREATE`, `ALTER`, and `DROP` privileges on the target database. Grant them to the Skyvern database user:

```sql
GRANT ALL PRIVILEGES ON DATABASE skyvern TO skyvern_user;
```

### Migration chain conflict after switching branches

If you switch Git branches (e.g., from a feature branch back to `main`) and the two branches have diverging migrations, `alembic current` may show a revision that does not exist in the checked-out branch's `alembic/versions/`. Alembic will refuse to upgrade or downgrade.

Resolution:

1. Identify the last common ancestor revision using `git log --oneline alembic/versions/`.
2. Use `alembic downgrade <ancestor-revision>` to roll back to a known-good state.
3. Switch branches, then run `alembic upgrade head`.

Always back up your database before resolving branch conflicts in a production environment.

### Server errors on startup without running migrations first

Starting the Skyvern server on an out-of-date schema typically produces errors such as:

- `column "X" of relation "Y" does not exist` — a migration added a required column that is missing
- `relation "Z" does not exist` — a migration created a table that was never applied
- `invalid input value for enum "..."` — a migration added an enum value that the old schema does not have

If you see any of these errors on startup, stop the server, run `alembic upgrade head`, and restart.
