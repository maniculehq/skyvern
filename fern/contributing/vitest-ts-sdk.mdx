The `@skyvern/client` TypeScript SDK (located in `skyvern-ts/client/`) has an 18-file Vitest test suite split into two projects: **unit** tests for HTTP infrastructure and **wire** tests that validate the SDK against a mock HTTP server. This guide explains how to run both, what they cover, and how to write custom tests.

## Prerequisites

- **Node.js ≥ 18** (the TS SDK target; Node.js 20 recommended to match the rest of the repo)
- **pnpm 10.14.0** — the SDK uses pnpm as its package manager

Install pnpm if you don't have it:

```bash
npm install -g pnpm@10.14.0
```

Install dependencies from `skyvern-ts/client/`:

```bash
cd skyvern-ts/client
pnpm install
```

## Running the tests

All commands run from `skyvern-ts/client/`.

| Command | What runs |
|---------|-----------|
| `pnpm test` | Both unit and wire projects |
| `pnpm test:unit` | Unit project only (`vitest --project unit`) |
| `pnpm test:wire` | Wire project only (`vitest --project wire`) |

```bash
# Run everything
pnpm test

# Run only unit tests (faster, no mock server spin-up)
pnpm test:unit

# Run only wire tests (API contract tests)
pnpm test:wire
```

## Unit tests

Unit tests are in `tests/unit/` and cover the Fern-generated HTTP fetcher infrastructure that underlies every SDK call. They run in a Node environment with no external dependencies.

## Wire tests

Wire tests are in `tests/wire/` and validate the generated `SkyvernClient` against a local mock HTTP server. They use [MSW (Mock Service Worker)](https://mswjs.io/) running in Node mode — no live Skyvern server is needed.

### How the mock server works

The mock server infrastructure lives in `tests/mock-server/`:

- **`MockServerPool.ts`** — owns the single MSW server instance and exposes `createServer()` to mint per-test `MockServer` contexts
- **`MockServer.ts`** — per-test server context with typed endpoint builders
- **`mockEndpointBuilder.ts`** — fluent API for registering expected request/response pairs
- **`setup.ts`** — Vitest `beforeAll`/`afterAll` hooks that call `mockServerPool.listen()` and `mockServerPool.close()`

Each wire test creates a `SkyvernClient` pointing at `server.baseUrl` (a random local port), registers expected endpoints via a fluent builder, then calls the client methods and asserts responses.

```typescript
// Simplified example of the wire test pattern
const server = mockServerPool.createServer();
const client = new SkyvernClient({ apiKey: "test", environment: server.baseUrl });

server
    .mockEndpoint()
    .post("/v1/run/tasks")
    .jsonBody({ prompt: "Find the top 3 posts on Hacker News." })
    .respondWith()
    .statusCode(200)
    .jsonBody({ run_id: "tsk_123", status: "created" })
    .build();

const response = await client.runTask({ body: { prompt: "Find the top 3 posts on Hacker News." } });
expect(response.run_id).toBe("tsk_123");
```

### Wire test inventory

| File | What it covers |
|------|---------------|
| `tests/wire/main.test.ts` | Comprehensive happy-path tests for all Skyvern REST API endpoints (~150 KB / 4,086 lines; auto-generated by Fern) |
| `tests/wire/artifacts.test.ts` | `getArtifactContent` — success (200) and error (403 / 404 / 422) paths |
| `tests/wire/scripts.test.ts` | `runScript` — success (200) and 422 error path |

<Note>
The wire tests are generated by Fern from the OpenAPI spec. Do not edit `main.test.ts`, `artifacts.test.ts`, or `scripts.test.ts` directly — changes will be overwritten on the next `fern generate` run.
</Note>

## Adding custom tests

`tests/custom.test.ts` is the designated location for hand-written SDK tests.

<Note>
Protect `tests/custom.test.ts` from being overwritten on the next `fern generate` run by creating `skyvern-ts/client/.fernignore` (if it does not already exist) and adding the path:

```
tests/custom.test.ts
```
</Note>

To add custom tests:

1. Open `tests/custom.test.ts`
2. Replace or extend the placeholder `describe` block:

```typescript
import { SkyvernClient } from "../src";

describe("custom tests", () => {
  it("initialises a client with an API key", () => {
    const client = new SkyvernClient({ apiKey: "test-key" });
    expect(client).toBeDefined();
  });

  it("sends the correct Authorization header", async () => {
    // Use MockServerPool for any tests that need HTTP assertions
    // (see wire test pattern above)
  });
});
```

The `custom.test.ts` file is picked up by the **unit** project (it sits in the `tests/` root, which the unit project includes via `include: ["**/*.test.{js,ts,jsx,tsx}"]`).

## Gotchas and edge cases

The following non-obvious behaviours are captured in the unit test suite and are worth knowing before you extend it.

### requestWithRetries — retry semantics

The fetcher retries on **408, 429, 500, and 502** status codes only. Other 4xx and 5xx codes (e.g. 400, 403, 404, 503) are returned immediately without retrying.

The `maxRetries` parameter counts *extra* attempts, not total calls. `maxRetries=2` means up to **3** HTTP calls (1 initial + 2 retries):

```typescript
requestWithRetries(() => fetch(url), 2);
// → at most 3 calls if all return 500
```

Backoff uses exponential doubling with jitter, starting at 1 second: 1 s → 2 s → 4 s → … up to a hard cap of **60 seconds** (`MAX_RETRY_DELAY`). A `Retry-After: 120` header would normally request a 120-second wait but gets capped at 60 seconds.

Two header forms are respected for rate-limit delays:

| Header | Format | Example |
|--------|--------|---------|
| `Retry-After` | Integer seconds | `Retry-After: 5` → wait 5 s |
| `Retry-After` | HTTP date string | `Retry-After: Wed, 15 Apr 2026 00:00:00 GMT` |
| `X-RateLimit-Reset` | Unix timestamp (seconds) | `X-RateLimit-Reset: 1744675200` |

The tests use `vi.useFakeTimers()` and mock `Math.random` to `0.5` for deterministic jitter. If you write tests for retry logic, replicate this setup or the backoff assertions will be flaky.

### toQueryString — array and null serialisation

`toQueryString` (from `core/url`) has several subtle behaviours that differ from common expectations:

- **Arrays default to index notation**: `{ items: ["a", "b"] }` → `items%5B0%5D=a&items%5B1%5D=b`. Pass `{ arrayFormat: "repeat" }` to get `items=a&items=b`.
- **`null` becomes an empty string**; `undefined` is **omitted** at the top level:
  ```typescript
  toQueryString({ age: null, email: undefined, name: "Jo" })
  // → "age=&name=Jo"   (email dropped entirely)
  ```
- **`undefined` in arrays skips the index**; `null` keeps it:
  ```typescript
  toQueryString({ items: ["a", null, "c", undefined, "e"] })
  // → "items%5B0%5D=a&items%5B1%5D=&items%5B2%5D=c&items%5B4%5D=e"
  //                                                   ↑ index 3 absent
  ```
- **Primitive top-level values return empty string**: passing `"hello"` or `42` directly (not wrapped in an object) silently returns `""`.

### FormDataWrapper — setup requirement

`FormDataWrapper` is a two-phase object: you must call `await formData.setup()` before appending anything. Forgetting `setup()` will cause a runtime error. The factory function `newFormData()` runs setup automatically and is the preferred approach:

```typescript
// ✓ factory — setup included
const fd = await newFormData();
fd.append("field", "value");

// ✓ manual — setup must be explicit
const fd = new FormDataWrapper();
await fd.setup();
fd.append("field", "value");
```

Other `FormDataWrapper` behaviours captured in the tests:

- A `Blob` appended without an explicit `filename` option gets the filename `"blob"`.
- A `File` object's built-in filename can be overridden by passing `{ data: file, filename: "override.txt" }`.
- `Readable` streams with a `.path` property have their filename auto-detected, including Windows-style paths (`C:\test\path\file.txt` → `"file.txt"`).
- `getRequest()` always returns `{ body: FormData, headers: {}, duplex: "half" }`. The headers object is intentionally empty — the runtime (undici / browser fetch) injects the `Content-Type: multipart/form-data; boundary=…` header automatically.

### globals: true and custom test imports

The `vitest.config.ts` sets `globals: true` for both the unit and wire projects. Generated test files rely on this (no explicit `import { describe, it, expect } from "vitest"`). `tests/custom.test.ts` is part of the **unit** project and also benefits from globals, but you may import explicitly if your linter or editor's type-checking requires it — both styles work.

### Wire test port allocation

Each `mockServerPool.createServer()` call binds to a random local port, so parallel test runs (e.g. `--shard` or concurrent CI jobs) do not conflict. You do not need to manage ports manually.

## Configuration reference

`skyvern-ts/client/vitest.config.ts`:

```typescript
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    projects: [
      {
        test: {
          globals: true,        // No need to import describe/it/expect
          name: "unit",
          environment: "node",
          root: "./tests",
          include: ["**/*.test.{js,ts,jsx,tsx}"],
          exclude: ["wire/**"], // Wire tests excluded from unit project
        },
      },
      {
        test: {
          globals: true,
          name: "wire",
          environment: "node",
          root: "./tests/wire",
          setupFiles: ["../mock-server/setup.ts"], // Starts MSW before tests
        },
      },
    ],
    passWithNoTests: true,
  },
});
```

Key points:
- **`globals: true`** — `describe`, `it`, `expect`, and other Vitest globals are injected automatically; no import needed in generated test files (though custom files may import them explicitly).
- **Dual-project setup** — `pnpm test:unit` and `pnpm test:wire` run isolated subsets; `pnpm test` runs both.
- **`passWithNoTests: true`** — the test run does not fail if no files match.
