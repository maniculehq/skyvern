Skyvern's Vitest test suites (frontend and TypeScript SDK) are **not currently executed in CI**. This page explains the current state and shows the minimal workflow changes needed to gate them on every pull request.

Before reading this page, see [Testing the Skyvern UI (Vitest)](/contributing/vitest-frontend) and [Testing the TypeScript SDK (Vitest)](/contributing/vitest-ts-sdk) for an explanation of what each suite covers and how to run it locally.

## Current state

The CI workflow (`.github/workflows/ci.yml`) runs three things:

| Job | What it does |
|-----|-------------|
| `test` | `uv run pytest` (Python unit tests) + `pre-commit` hooks + Alembic migration check |
| `fe-lint-build` | `npm run lint` + `npm run build` in `skyvern-frontend/` |
| *(none)* | `pnpm test` in `skyvern-ts/client/` — **not run** |

The `fe-lint-build` job installs Node.js dependencies and runs the linter and build but does **not** call `npm test` (which would run `vitest run`). There is no job for the TypeScript SDK at all.

## Adding frontend Vitest tests

Add a `npm test` step to the existing `fe-lint-build` job, after the build step:

```yaml
  fe-lint-build:
    name: Frontend Lint and Build
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: ./skyvern-frontend
    steps:
      - name: Check out Git repository
        uses: actions/checkout@34e114876b0b11c390a56381ad16ebd13914f8d5 # v4
        with:
          persist-credentials: false
      - name: Set up Node.js
        uses: actions/setup-node@49933ea5288caeca8642d1e84afbd3f7d6820020 # v4
        with:
          node-version-file: .nvmrc
      - name: Install Node.js dependencies
        run: npm ci
      - name: Run linter
        run: npm run lint
      - name: Run build
        run: npm run build
      # ↓ Add this step
      - name: Run Vitest (frontend)
        run: npm test
```

`npm test` executes `vitest run` — a single non-interactive pass that exits with code 0 on success. The `passWithNoTests: true` flag in `vitest.config.ts` ensures the job does not fail if a branch introduces no test files.

## Adding TypeScript SDK Vitest tests

Add a new job to `.github/workflows/ci.yml`:

```yaml
  ts-sdk-test:
    name: TypeScript SDK Tests (Vitest)
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: ./skyvern-ts/client
    steps:
      - name: Check out Git repository
        uses: actions/checkout@34e114876b0b11c390a56381ad16ebd13914f8d5 # v4
        with:
          persist-credentials: false
      - name: Set up Node.js
        uses: actions/setup-node@49933ea5288caeca8642d1e84afbd3f7d6820020 # v4
        with:
          node-version: "20"
      - name: Install pnpm
        uses: pnpm/action-setup@v3
        with:
          version: "10.14.0"
      - name: Install dependencies
        run: pnpm install
      - name: Run unit tests
        run: pnpm test:unit
      - name: Run wire tests
        run: pnpm test:wire
```

The unit and wire tests run as separate steps so failures are reported independently. Both use the MSW mock server (no live Skyvern server needed) and complete in seconds.

<Tip>
If you only want to run unit tests (faster, no mock-server spin-up) in a first pass, use `pnpm test:unit` and add a follow-up step for `pnpm test:wire` guarded by a path filter.
</Tip>

## Scoping jobs with path filters

If you want to skip the TypeScript SDK tests when no SDK files changed, add a `paths` filter to the trigger. The job still runs on every PR against `main` when the filter is omitted, which is the simpler starting point.

```yaml
on:
  pull_request:
    paths:
      - "skyvern-ts/client/**"
      - ".github/workflows/ci.yml"
```

Apply the same pattern to the frontend job if you want to gate it only on changes under `skyvern-frontend/`. Keep `.github/workflows/ci.yml` in every `paths` list so that CI-config changes always trigger a full run.

<Warning>
Path filters interact with GitHub's required-status-check feature. If a job is skipped because no matching paths changed, GitHub records it as "skipped" rather than "passed". When the job is a required status check, **skipped** may count as a failure depending on your branch protection settings. Consider using the `paths-ignore` inverse pattern or the [`actions/skip-duplicate-runs` action](https://github.com/marketplace/actions/skip-duplicate-runs) to handle this cleanly.
</Warning>

## `passWithNoTests` and safe rollout

Both `skyvern-frontend/vitest.config.ts` and `skyvern-ts/client/vitest.config.ts` set `passWithNoTests: true`. This means:

- A branch that **does not change** any test file will still pass the Vitest step.
- A branch that **deletes** all test files will also pass — the flag does not protect against accidental deletion.

If you want stricter protection, remove `passWithNoTests: true` after adding initial test coverage; the test run will then fail if the `include` glob matches zero files.

## Recommended rollout

1. **Add frontend Vitest step** first — it is a low-risk addition to an existing job and uses existing Node setup. See [Testing the Skyvern UI (Vitest)](/contributing/vitest-frontend) for the full test inventory.
2. **Add the TS SDK job** — it requires pnpm setup but is otherwise self-contained. See [Testing the TypeScript SDK (Vitest)](/contributing/vitest-ts-sdk) for the full test inventory.
3. **Remove `passWithNoTests: true`** from both configs once the baseline test count is stable, to prevent accidental regressions.

## Version pinning notes

**`pnpm/action-setup`**: The YAML above uses `@v3`. Pin to a specific commit SHA in production (matching the pattern used by other actions in `ci.yml`) to avoid unexpected breakage from upstream action changes.

**Node.js version**: The TS SDK job uses `node-version: "20"` rather than the `.nvmrc` file because `skyvern-ts/client/` does not ship its own `.nvmrc`. If that changes, switch to `node-version-file: skyvern-ts/client/.nvmrc` to keep the version consistent.

**Wire test isolation**: Each test call to `mockServerPool.createServer()` binds the MSW server to a random local port. This means multiple CI shards or concurrent workflow runs never compete for the same port — no additional configuration is needed.
