Workflow blocks are the building blocks of Skyvern workflows. Each block performs a specific function; blocks run in sequence (or in loops) to achieve your automation goal.

Blocks are assembled in the [Workflow Editor](/workflows/manage-workflows). Parameters referenced in block fields use [Jinja2 syntax](/workflows/workflow-parameters) — for example, `{{my_param}}` or `{{block_name_output}}`.

## Navigation Block

Navigates through a website to accomplish a goal. The agent takes as many actions as needed (up to `max_steps_per_run`) to complete the navigation goal.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `navigation_goal` | string | Yes | Natural language goal for the navigation (e.g. "Search for running shoes and add the first result to cart") |
| `url` | string | No | Starting URL. If omitted, continues from the current browser state |
| `max_steps_per_run` | integer | No | Step limit for this block (overrides workflow default) |
| `complete_criterion` | string | No | Jinja expression or natural language condition; block completes early when true |
| `terminate_criterion` | string | No | Condition that terminates the workflow (marks as failed) |
| `data_schema` | object | No | JSON Schema for data to extract at the end of navigation |
| `error_code_mapping` | object | No | Map error conditions to custom error codes |

## Action Block

Like the Navigation Block but takes **only one action** and stops. Use this when you need precise, atomic control over a single browser interaction.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `navigation_goal` | string | Yes | Natural language instruction for the single action to take (e.g. "Click the Submit button") |
| `url` | string | No | URL to navigate to before taking the action |
| `max_steps_per_run` | integer | No | Step limit (default: 1 for a single-action block) |
| `error_code_mapping` | object | No | Map error conditions to custom error codes |

## Extract Block

Extracts structured data from the current page without taking any navigation actions.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `data_extraction_goal` | string | Yes | Description of what to extract |
| `data_schema` | object | No | JSON Schema defining the structure of extracted data |

Use this block when you want to capture information from a page that has already been navigated to.

## Login Block

Handles login flows with stored credentials. Skyvern never sends your password to the LLM — credentials are injected directly into the browser.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `url` | string | No | Login page URL (navigates there first if provided) |
| `navigation_goal` | string | No | Custom login instructions (useful for non-standard login flows) |
| `max_steps_per_run` | integer | No | Step limit for the login flow |

When a website has an unusual login flow (CAPTCHA, multi-step verification, custom username field), add a custom `navigation_goal` with additional instructions.

## Validation Block

Asserts the current workflow state. Evaluates conditions without taking browser actions. If `terminate_criterion` evaluates to true (or `complete_criterion` is false), the workflow is terminated — like an assertion in a test. The ValidationBlock cannot be the first block in a workflow.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `complete_criterion` | string | No | Condition that marks the validation as passed (natural language or Jinja expression) |
| `terminate_criterion` | string | No | Condition that terminates the workflow as failed |
| `error_code_mapping` | object | No | Map validation failures to specific error codes |

## Task Block

The general-purpose block that combines navigation, data extraction, and validation. Use the Navigation Block for pure navigation and the Extract Block for pure extraction when you want cleaner separation of concerns.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `url` | string | No | Starting URL for the task |
| `navigation_goal` | string | No | Goal for browser navigation |
| `data_extraction_goal` | string | No | What data to extract |
| `data_schema` | object | No | JSON Schema for extracted data |
| `complete_criterion` | string | No | Condition to complete the block early |
| `terminate_criterion` | string | No | Condition to terminate the workflow |
| `max_steps_per_run` | integer | No | Step limit |
| `error_code_mapping` | object | No | Custom error code mapping |

## ForLoopBlock

Iterates over a list, running a set of child blocks once per item.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `loop_over` | parameter reference | Yes | The list parameter to iterate over |
| `loop_blocks` | block list | Yes | Blocks to run for each iteration |

**Reserved variables inside a for loop:**

| Variable | Description |
|---|---|
| `{{current_value}}` | The current item in the list |
| `{{current_item}}` | Alias for `{{current_value}}` |
| `{{current_index}}` | Zero-based index of the current iteration |

These variables are also documented in the [Reserved Parameters](/workflows/workflow-parameters#reserved-parameters) section alongside all other built-in Jinja variables.

<Warning>
**Cross-loop reference restriction**: you cannot reference a block that is *inside* a `ForLoopBlock` from *outside* the loop. The inner blocks' outputs are scoped to their loop iteration. If you need to aggregate results across all iterations, collect them inside the loop (e.g. using a `CodeBlock` or `TextPromptBlock`) and reference the loop block's own output after it finishes.
</Warning>

```yaml
# Example workflow snippet: iterate over a list of URLs
parameters:
  - key: urls
    parameter_type: workflow
    default_value:
      - "https://example.com/page1"
      - "https://example.com/page2"

blocks:
  - block_type: for_loop
    label: process_each_url
    loop_over:
      parameter_type: workflow_parameter
      key: urls
    loop_blocks:
      - block_type: navigation
        navigation_goal: "Extract the page title from {{current_value}}"
        url: "{{current_value}}"
```

## TaskV2Block (NavigationV2Block)

The advanced version of the Navigation Block powered by the **Skyvern 2.0** engine. Designed for complex, multi-page tasks with high accuracy requirements.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `url` | string | No | Starting URL |
| `prompt` | string | Yes | Complex goal for the agent |
| `max_iterations` | integer | No | Overrides `MAX_ITERATIONS_PER_TASK_V2` (default 10) |
| `max_steps` | integer | No | Step limit per run |

Use this block when `skyvern-2.0` accuracy is needed within a workflow. [See the Engine Selection Guide](/running-tasks/run-tasks#engine-selection-guide) for a comparison of all available engines.

## Url Block

Navigates the browser to a specific URL. Equivalent to a `goto` in code.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `url` | string | Yes | URL to navigate to (supports Jinja parameter references) |

## Code Block

Runs arbitrary Python and Playwright code in the browser context. Available to all self-hosted deployments; **invite-only on Skyvern Cloud** (contact support@skyvern.com).

| Parameter | Type | Required | Description |
|---|---|---|---|
| `code` | string | Yes | Async Python code. May use `page` (Playwright) and any parameters you list in `parameters` |
| `parameters` | list | No | Workflow parameters to inject as local variables by their key name |

### Execution environment

The code runs inside an `async def wrapper()` function. It receives:
- **`page`**: a `SkyvernBrowserPage` (Playwright `Page` extension with AI methods such as `act()`, `extract()`, `validate()`)
- **Your parameters by name**: any parameter key listed in `parameters` is injected as a local variable — for example, a parameter with key `search_query` is available as the local variable `search_query`
- **Limited builtins**: `print`, `len`, `range`, `str`, `int`, `float`, `dict`, `list`, `tuple`, `set`, `bool`, `sleep`, `asyncio.sleep`, `re`, `json`, `Exception`

### Block output

The block output is a **dictionary of all local variables** at the end of execution. Whatever you assign to local variables becomes accessible to later blocks via `{{your_block_label_output.variable_name}}`.

```python
# Example: get page title and extract structured data
title = await page.title()

data = await page.extract(
    "Extract the product name and price",
    schema={
        "type": "object",
        "properties": {
            "name": {"type": "string"},
            "price": {"type": "number"},
        },
    },
)

product_name = data.get("name", "")
product_price = data.get("price", 0)
# Later blocks can reference {{your_block_label_output.title}},
# {{your_block_label_output.product_name}}, etc.
```

### Jinja in code

The `code` field itself is rendered as a Jinja template before execution, so you can inline workflow parameter values directly:

```python
await page.goto("{{target_url}}")
await page.act("Search for {{search_query}}")
result = await page.extract("Extract the search results count")
count = result.get("count", 0)
```

### Sandbox restrictions

The code block enforces a blocklist-based sandbox. The following are **not allowed**:

- `import` statements — all module imports are blocked. Use the pre-injected `re`, `json`, and `asyncio.sleep` for common needs.
- Dunder attribute access (`obj.__class__`, `obj.__dict__`, etc.)
- Subprocess creation (`popen`, `system`, `create_subprocess_exec`, etc.)
- Direct filesystem operations (`listdir`, `makedirs`, etc.)
- `eval`, `exec`, `getattr`, `setattr`, `globals`, `vars`

<Warning>
The sandbox is a blocklist, not process-level isolation. Do not rely on it as a security boundary in multi-tenant deployments. For production use, keep CodeBlock access restricted to trusted users.
</Warning>

## TextPromptBlock

Sends a text-only prompt to the LLM and stores the response as block output. No browser interaction occurs.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `llm_key` | string | No | Override the model for this block |
| `prompt` | string | Yes | Prompt to send to the LLM (supports Jinja) |
| `json_schema` | object | No | JSON Schema to structure the LLM response |

Use this block to transform data between steps (e.g. reformat a scraped address, summarize text).

## ConditionalBlock

Branches the workflow based on ordered conditions. Evaluates each `BranchCondition` top-to-bottom and runs the block pointed to by the first matching condition.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `branch_conditions` | list | Yes | Ordered list of `BranchCondition` objects evaluated top-to-bottom. The first matching condition determines which block to run next |

Each `BranchCondition` has:

| Field | Type | Description |
|---|---|---|
| `criteria` | object | A `JinjaBranchCriteria` or `PromptBranchCriteria` expression (omit for the default branch) |
| `next_block_label` | string | Label of the block to run when this condition matches |
| `is_default` | boolean | When `true`, this branch runs if no other conditions match (acts as `else`). No `criteria` allowed |
| `description` | string | Optional human-readable note about this branch |

**Condition types:**
- **Jinja expression** (`JinjaBranchCriteria`): `{ "criteria_type": "jinja2_template", "expression": "{{ items | length > 0 }}" }` — evaluated as a Python boolean with Jinja rendering
- **Natural language** (`PromptBranchCriteria`): `{ "criteria_type": "prompt", "expression": "Did the previous extraction find any results?" }` — the LLM evaluates against current context
- **Default branch**: `{ "is_default": true, "next_block_label": "fallback_block" }` — runs if no other condition matches

A `ConditionalBlock` must have at least one branch and at most one default branch.

## HttpRequestBlock

Makes an HTTP request from the workflow (server-side, not the browser).

| Parameter | Type | Required | Description |
|---|---|---|---|
| `method` | string | Yes | HTTP method (GET, POST, PUT, PATCH, DELETE) |
| `url` | string | Yes | Request URL (supports Jinja) |
| `headers` | object | No | Request headers as key-value pairs |
| `body` | object or string | No | Request body (JSON object or string; supports Jinja) |
| `timeout` | integer | No | Request timeout in seconds |

The response is stored as block output and can be referenced by later blocks via `{{block_name}}`.

## SendEmailBlock

Sends an email via SMTP.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `smtp_host` | string | Yes | SMTP server hostname (references an AWSSecretParameter key) |
| `smtp_port` | string | Yes | SMTP port (e.g. `587`) (references an AWSSecretParameter key) |
| `smtp_username` | string | Yes | SMTP username (references an AWSSecretParameter key) |
| `smtp_password` | string | Yes | SMTP password (references an AWSSecretParameter key; use an app password for Gmail) |
| `sender` | string | Yes | Sender email address (supports Jinja) |
| `recipients` | list | Yes | List of recipient email addresses |
| `subject` | string | Yes | Email subject (supports Jinja) |
| `body` | string | Yes | Email body (supports Jinja) |
| `file_attachments` | list | No | Attachment file paths or download URLs |

## FileParserBlock

Parses PDFs, CSVs, and Excel files. Returns structured data from the file.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `file_url` | string | Yes | URL of the file to parse (supports Jinja for dynamic file URLs from previous blocks) |
| `file_type` | string | Yes | File type: `pdf`, `csv`, `excel`, `image`, or `docx` |

## DownloadToS3Block / UploadToS3Block

Transfers files between the browser/workflow and AWS S3.

**DownloadToS3Block** — downloads a file from a URL and uploads it to the configured S3 bucket (set via `AWS_S3_BUCKET_UPLOADS` env var). The uploaded S3 URI is stored as the block output.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `url` | string | Yes | File URL to download (supports Jinja) |

**UploadToS3Block** — uploads a file that was downloaded during the workflow to S3.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `path` | string | No | Directory path within the workflow's download folder to upload. Defaults to the entire workflow download directory |

## FileUploadBlock

Uploads files from the workflow's download directory to cloud storage (S3 or Azure Blob Storage).

| Parameter | Type | Required | Description |
|---|---|---|---|
| `storage_type` | string | No | `S3` (default) or `AZURE` |
| `s3_bucket` | string | No | Destination S3 bucket (required when `storage_type=S3`) |
| `aws_access_key_id` | string | No | AWS access key ID (supports Jinja) |
| `aws_secret_access_key` | string | No | AWS secret access key (supports Jinja) |
| `region_name` | string | No | AWS region (supports Jinja) |
| `azure_storage_account_name` | string | No | Azure storage account name |
| `azure_storage_account_key` | string | No | Azure storage account key |
| `azure_blob_container_name` | string | No | Azure Blob container name |
| `path` | string | No | Local path within the download directory to upload |

## WaitBlock

Pauses the workflow for a fixed time.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `wait_sec` | integer | Yes | Seconds to wait (max: `WORKFLOW_WAIT_BLOCK_MAX_SEC`, default cap 1800s) |

## HumanInteractionBlock

Pauses the workflow and waits for a human to take an action before continuing. If the human chooses negatively or the timeout expires, the workflow terminates.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `instructions` | string | No | Instructions shown to the human operator |
| `positive_descriptor` | string | No | Label for the "continue" / approve action (default: "Approve") |
| `negative_descriptor` | string | No | Label for the "stop" / reject action (default: "Reject") |
| `timeout_seconds` | integer | No | Seconds to wait for human response before auto-terminating |

## WorkflowTriggerBlock

Triggers another workflow run from within the current workflow. Useful for composing workflows as sub-workflows.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `workflow_permanent_id` | string | Yes | Permanent ID of the workflow to trigger |
| `payload` | object | No | Parameters to pass to the triggered workflow as key-value pairs |
| `wait_for_completion` | boolean | No | Whether to wait for the triggered workflow to finish before continuing (default: `true`) |
| `browser_session_id` | string | No | Optional browser session for the triggered workflow |
| `use_parent_browser_session` | boolean | No | When `true`, the child workflow inherits the parent's browser session (default: `false`) |
